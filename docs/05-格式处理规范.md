# 05 格式处理规范

## 1. 两种“无损”

| 层级 | 含义 | 本项目要求 |
|---|---|---|
| 像素无损 | 还原像素逐个相同，文件字节可能不同 | 不够 |
| **文件字节无损** | 还原文件与原文件逐字节相同，SHA-256 一致 | **必须** |

## 2. 通用处理流程

```
原文件 ─► SHA-256 ─► detect（按内容识别）
                       │
          ┌────────────┴─────────────┐
     可识别且可压缩                无法识别 / 不可压缩
          │                           │
   parse：拆分为                    zstd（压大了就原样）
   · 原样字节段（文件头、调色板、标签、填充、文件尾）
   · 像素数据
          │
   layout：版面整理（翻转行序、去填充、字节序、解包、移位、Bayer 拆分）
          │
   codec：图像编码
          │
   verify：解码 → 逆版面 → 拼回原样字节段 → SHA-256 比对
          │
     一致 → 写入容器      不一致 → 回退 zstd / 原样，并记录日志
```

## 3. 格式优先级

| 优先级 | 格式 |
|---|---|
| **P0 首发** | BMP、TIFF（未压缩）、RAW 裸数据、Bayer、TIFF LZW/ZIP（仅复现式还原通过时） |
| P1 按需 | 16 位 OME-TIFF 堆栈、DICOM 未压缩、FITS、未压缩 DNG/CinemaDNG、未压缩相机 RAW、未压缩视频/图像序列、EXR 无压缩、TGA/DDS、HDF5/Zarr |
| P2 可选 | JPEG（JPEG XL 无损转码或 Lepton，约省 20%，可逐字节还原）、PNG（复现式还原）、PSD/PSB（暂不做） |
| 不处理 | HEIC/AVIF/WebP/JPEG 2000/JPEG XL、MP4/MOV/MKV、ProRes、已压缩相机 RAW（CR3 等）、EXR PIZ/ZIP/DWAA、压缩包、加密文件 → 原样存储 |

## 4. P0 格式细则

### 4.1 BMP

| 要点 | 处理 |
|---|---|
| DIB 头版本：40 / 108 / 124 字节等 | 文件头整段原样保存，不重建 |
| 8 位带 1024 字节调色板 | 原样保存；灰度调色板时像素按灰度编码；非灰度调色板按索引编码 |
| 高度为正时自下而上存储 | 编码前翻成自上而下，记录方向 |
| 每行 4 字节对齐填充 | 校验填充字节；全 0 只记标志，非 0 单独保存 |
| 24/32 位 BGR/BGRA | 可逆色彩变换后编码；Alpha 多为常量 |
| 文件尾附加数据 | 原样保存 |

### 4.2 TIFF

| 要点 | 处理 |
|---|---|
| II / MM 字节序 | 16 位大端先转换再编码，记录 |
| 条带 / 图块、多页 | 只替换像素块，IFD 与所有偏移原样记录 |
| 厂商私有标签 | 原样保存 |
| 8 / 12 / 16 位 | 统计实际最大值，传给编码器（JPEG-LS MAXVAL / HTJ2K 位深） |
| BigTIFF | 支持 64 位偏移 |
| Compression ≠ 1（LZW / ZIP / PackBits） | 走复现式还原（见第 5 节）；失败则 zstd 兜底 |
| PlanarConfiguration、Predictor 标签 | 解析后按实际版面处理 |

注意：OpenCV `imwrite` 写 TIFF 默认使用 LZW 压缩，现场大量“TIFF”可能不是未压缩的。

### 4.3 RAW 裸数据

| 要点 | 处理 |
|---|---|
| 无文件头 | 参数来源按优先级：工位/目录规则配置 → 同名参数文件 → 文件大小反推候选（宽 × 高 × 字节数） |
| 像素格式 | Mono8、Mono10/12/16，打包格式 Mono10p、Mono12p、Mono12Packed（GenICam PFNC）→ 解包为 16 位编码，还原时按原格式重新打包 |
| 16 位容器中的 10/12 位数据 | 判断低位对齐还是**高位对齐**；高位对齐时右移后编码并记录移位量 |
| 行末填充 | 同 BMP 处理 |
| 参数推断错误 | verify 必然失败 → 回退兜底，不会损坏数据 |

### 4.4 Bayer

| 要点 | 处理 |
|---|---|
| 常伪装成灰度 BMP / TIFF / RAW | 用 2×2 周期统计自动检测棋盘格特征（四个相位子图的均值/方差差异） |
| 直接按灰度压缩预测失效 | 拆成 R、Gr、Gb、B 四个子平面分别编码，预计比直接压多省 20~40% |
| RGGB / BGGR / GRBG / GBRG | 拆分不需要知道排列；做通道间去相关（如 R−G）时需要，自动推断或配置 |
| 奇数宽高 | 边界行列单独处理 |
| 组合情况 | 按“解包 → 移位 → Bayer 拆分”顺序处理，逆序还原 |

## 5. 复现式还原（已压缩格式）

工业现场文件基本来自少数库：OpenCV、libtiff、Halcon、相机 SDK，且编码过程确定。

1. 解出像素，用候选库和参数重新编码；
2. 与原文件逐字节一致 → 只存“像素压缩流 + 编码器标识 + 参数”，读取时重新生成原文件；
3. 不一致 → zstd 兜底。

要求：设备内必须固定并归档所用编码库的版本，否则未来无法复现。复现所用库版本要写进容器。

## 6. 编码器选择

| 场景 | 默认编码器 |
|---|---|
| 8~16 位灰度、实时 | JPEG-LS |
| 大图、高吞吐、GPU | HTJ2K |
| 归档档 / 离线重压 | JPEG XL 无损 |
| 非图像 / 兜底 | zstd |

## 7. 容器格式草案（v0，待评审）

扩展名暂定 `.iis`。小端序。

```
Header
  magic          8 bytes   "IISCONT\0"
  version        u16
  flags          u16
  orig_size      u64       原文件字节数
  orig_sha256    32 bytes  原文件 SHA-256
  recipe_len     u32
  recipe         JSON(UTF-8)  版面与重组配方
  segment_count  u32
Segment[]  （按原文件顺序重组）
  type           u8        0=原样字节 1=zstd字节 2=图像码流 3=复现式码流
  codec          u8        0=none 1=jpegls 2=htj2k 3=jxl 4=zstd
  orig_offset    u64       在原文件中的偏移
  orig_length    u64       在原文件中的长度
  data_length    u64
  crc32c         u32       本段数据校验（防介质损坏，不替代 SHA-256）
  data           bytes
```

`recipe` 示例（8 位 BMP，自下而上，带填充）：

```json
{
  "format": "bmp",
  "width": 2448, "height": 2048, "channels": 1, "bits": 8,
  "row_order": "bottom_up",
  "row_stride": 2448, "row_padding": {"bytes": 0, "all_zero": true},
  "bayer": null,
  "shift": 0,
  "codec_params": {"jpegls": {"near": 0}},
  "lib_versions": {"charls": "x.y.z"}
}
```

设计原则：图像码流段是标准码流，可被任何标准解码器直接解开；配方公开文档化；独立开源解码器只依赖标准库。
